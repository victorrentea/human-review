  1. context Local only: the working tree has addVisitToOwner stripped of its vet handling

    Not a defect in the change set — HEAD is intact. An uncommitted edit in the working tree removes four things from addVisitToOwner: the VetRepository import, the field, @Validated on the body, and the whole if (vetId != null) setVet(...) block — +1 −6. Because the Add Visit form posts to that owner-scoped endpoint (visit.service.ts:34), booking through the UI silently drops the vet as the tree stands now: a bare curl returns 201 with vetId: null, the e2e scenario is red, and the video narrates it.

    Listed so the red test and the video are not mistaken for a defect in the branch. git checkout -- petclinic-backend/src/main/java/victor/training/petclinic/rest/OwnerRestController.java restores it. Everything below is about the committed change.

  2. must look The new foreign key makes every seeded vet undeletable — DELETE /api/vets/{id} now returns 500

    vet_id INT REFERENCES vets (id) carries no ON DELETE clause, and nothing on the JPA side nulls it out: Visit is the owning side and Vet has no visits mapping. deleteVet just calls delete(vet), so Postgres raises a FK violation, which handleGeneralException turns into a 500. The backfill on line 8 assigns a vet to every seeded visit, so all six demo vets become undeletable the moment this migration runs.

    Your call: ON DELETE SET NULL on the constraint, or null the visits out in deleteVet. Either changes behaviour, and amending V9 in place will trip Flyway's checksum on any database that already ran it — which is why I left it. No test covers deleting a vet that has visits.

  3. must look The backfill hardcodes vet ids 1–6 and has no WHERE

    UPDATE visits SET vet_id = 1 + (id % 6) assumes vets holds exactly ids 1..6 — true only for a pristine V3 seed. Delete a vet and add another through the existing API before upgrading, and the UPDATE points at a missing id: FK violation, Flyway marks V9 failed, and the backend refuses to boot until someone repairs it by hand. And the comment above it ("every visit in the DB at this point comes from the V3 sample data") is false for any database that has been in use: visits created through the UI or booked over MCP silently acquire a fabricated attending vet.

    The commit's own design says a null vet is legitimate, and both the UI and the tests already render the — fallback — so this write buys a demo nicety at the price of a data-integrity assumption. House precedent (V5__clear_demo_owner_phone.sql) keys data fixes off a name, not a hardcoded id.

  4. worth a look PUT /api/visits/{id} silently clears the attending vet when vetId is absent

    The handler overwrites unconditionally, so an existing consumer that PUTs only {date, description} — a script, or a client generated from the OpenAPI spec before this change — now also wipes vet_id, with nothing in the response to say so. update_clearsTheAttendingVet blesses this as intended behaviour, which makes it a decision rather than a bug.

    Either document it as a breaking change to the endpoint, or distinguish "field absent" from "explicitly null" (a JsonNullable/PATCH split). Both are contract decisions.

  5. worth a look An unknown vetId answers 404, not 400

    getByIdOrNull throws a bare NoSuchElementException, which the advice maps to 404 with a plain-text "Not found!" body — not the ProblemDetail shape every other error uses. PUT /api/visits/5 with {"vetId": 999} on an existing visit 5 therefore returns a 404 that is indistinguishable from "visit 5 does not exist", and the Angular error handler surfaces the wrong message. A bad request field is a 400.

    Fixing it means picking an exception type and touching ExceptionControllerAdvice — a cross-cutting contract change, so it is yours. It applies to POST /api/visits too.

  6. nit @ManyToOne defaults to EAGER, so vets load on every visit-reading path

    Only findAllWithPetAndOwner got the LEFT JOIN FETCH v.vet. GET /api/pets, the owner-detail page and MCP list_visits each now issue extra SELECT … FROM vets when visits are materialised. The first-level cache bounds it to the number of distinct vets per session, so the cost is modest.

    I left it because fetch = LAZY risks a LazyInitializationException in the mappers that run outside a transaction — which is a correctness change disguised as a tuning knob, and needs your read on the other paths.

Fixed for you

Everything below came out of /code-review and /simplify and had exactly one defensible answer, so I applied it rather than spending your attention on it. Backend tests are green after these. Anything needing a judgement call went to Look here first instead.

1. The vet lookup had two homes

VisitRestController carried a private resolveVet that both of its write paths called. The null rule — "no vetId means no vet, an unknown one is rejected" — is a property of looking a vet up, not of a controller, so it moved onto the repository. Spring Data enforces @NonNullApi on repository methods, so the parameter needed an explicit @Nullable: without it the call throws before it reaches the body, and three tests went red on the first run.

2. Three tests were green for the wrong reason

VisitTest is @Transactional, so the test and the MockMvc-invoked controller share one persistence context. Every vet test asserted against the very instance the controller had just mutated in memory — they would have stayed green with visitRepository.save() deleted outright. They now flush and clear first, so the assertion reads the database.

3. The vet dropdown opened blank

Both forms started from this.visit = {} as Visit, leaving vetId undefined. The placeholder option binds to null, and undefined !== null for Angular's option lookup, so the select rendered with selectedIndex = -1 — empty — until the user touched it.

4. The same em-dash rule, written out twice

visit.vetFirstName ? visit.vetFirstName + ' ' + visit.vetLastName : '—' was spelled out inline in both visit-list templates. "No vet" is a display decision the whole app should make the same way, so it became a pipe — which also gets a long ternary out of a template.

.}}

5. The e2e vet picker depended on the placeholder's position

It selected option.nth(1) — "index 0 is the placeholder" encoded as an incidental fact about the template. Reorder the options, or add a second placeholder, and an unrelated scenario fails confusingly. It now picks the first option that actually carries a vet id.

6. A dead import

VisitRestController stopped naming the Vet type once the lookup moved to the repository. Removed.
